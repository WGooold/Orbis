# ADR-0020: Shared DeepSeek Harness Web backend

Date: 2026-09-26

Status: accepted. Web is the default DSH backend; ACP remains a legacy/test adapter without automatic fallback.

Update (2026-09-27): attaching every live Agent at startup scaled badly (dozens of Sessions meant dozens of follows and metadata broadcasts). Only working Agents now occupy an online card.

Update (2026-11-01): DSH is no longer gated by eager Host startup. When an App session request names DeepSeek, Host reuses an attached ready runtime; otherwise it creates the authenticated Web service connection on demand, starting the local service only when the verified descriptor is absent. `--dsh` and the desktop prestart setting only control eager preparation. Host announces DSH in `launchableAgents` only when it can resolve the local CLI and configuration.

Update (2026-11-05, implemented; device verification pending): desktop and CLI Hosts also recover existing DSH Web services independently of eager startup and App activation. The shared Host recovery interface runs at startup and every two seconds after each completed attempt. It authenticates the explicitly configured endpoint or the current per-home descriptor; passive discovery reuses only an authenticated existing service. Successful Web handshake loads the matching native decoder and attaches ordinary session discovery. Running Sessions are followed; idle/cold history, archives and subagents retain their existing rules. An already-ready bridge is reused without further service probes. Terminal connection failure permits the next probe to read fresh authentication metadata; transient transport rotation retains the existing Web client's reconnect behavior.

Automatic recovery and explicit App activation share one in-flight backend preparation. A passive probe that finds no service or fails cannot consume an explicit launch request: the App path may then ensure the service, but native Session operations and uncertain messages are never replayed. Passive recovery does not synchronize provider credentials or switch providers. Host pause closes the recovery gate, cancels the timer, waits for in-flight preparation and closes any late client before cleanup completes. The persistent Web process remains owned by its launcher.

Update (2026-11-06, implemented; Android acceptance pending): DSH-RECONNECT-01/02 bound a continuous carrier outage by the Web handshake timeout (15 seconds by default), including repeated connection refusals and sockets that never complete the native event handshake. Expiry retires the bridge through its existing offline callback so Host recovery can reread the current service descriptor. DSH-RECONNECT-03 clears that deadline only after a native ready frame; ordinary socket rotations retain their existing subscriptions and RPC behavior. DSH-RECONNECT-04 verifies fresh service discovery, opening the original Session and creating a new Session against an isolated official Web process. Implementation and tests: [dsh-web-client.ts](../../packages/host/src/dsh-web-client.ts), [dsh-web-client.test.ts](../../packages/host/src/dsh-web-client.test.ts), [test-dsh-web-reconnect.mjs](../../scripts/test-dsh-web-reconnect.mjs). Execution and delivery status: [verification.json](../../.artifacts/dsh-reconnection-timeout-20261106/verification.json).

## Context

The ACP backend could not share live execution with the DSH browser. Orbis now attaches both browser and mobile workflows to the same native Web service and Session.

## Decision

The Host authenticates to a loopback Web launch URL using its token. Without an explicit URL, it reuses a verified per-home descriptor or launches one persistent Web service under a cross-process lock. Host shutdown disconnects its transport, leaving that service and browser sessions running. A phone still requires an online Host.

An App request to create or resume a DeepSeek Session ensures this runtime before activation. The activation waits for service authentication, Web handshake and the native Session operation; opening a browser window or starting a child process alone does not report success. An already attached ready runtime is used directly.

The desktop Agent update flow is an explicit exception: after installing and verifying DSH, it restarts a running Orbis-owned Web service with the new CLI, keeping its home and port and publishing fresh authentication metadata. The update dialog explains the interruption before confirmation. Restart and service acquisition share the same cross-process lock; the authenticated descriptor PID must also own the listening socket before termination. External endpoints are left to their launcher, and unused services are not started by an installation. Failed or cancelled downloads do not restart the service. A failed restart or provider synchronization retains the verified installation and reports a separate warning. Ordinary Host shutdown and provider changes retain their existing non-terminating behavior.

The CLI installation supplies matching protocol validators and the assistant-stream decoder. Native session list/page/follow RPCs own discovery, canonical history, streaming, queue operations, model selection and approvals. Before creating or resuming a Session from the app, Orbis resolves its absolute `cwd` through `workspace/create` and passes the resulting `workspaceId` to `session/create`; this keeps browser Workspace grouping aligned with the app's directory tree. Workspace follow supplies the archive set. Entry IDs include `:web:` to keep this event mapping separate from the earlier ACP mapping. The ACP implementation remains a legacy/test adapter, without an automatic fallback.

The App's delivery queue contains human submissions from any frontend, identified by native `source.kind === "user"` (or source-less legacy messages). DSH also stores model-facing context in its user-role inbox: permission transitions (`user-approval`), adjacent-Agent messages (`agent-message`), background completion (`subagent-settled`), plugin context and automatic goal input are not human submissions. Host filters explicit non-user sources before queue identity, capacity and completeness checks, consistently with chat history, and never uses them to settle an App send receipt. A complete context-only inbox therefore publishes a complete empty user queue. Filtering does not remove or cancel native context, alter its persistence or prevent the Agent from consuming it; unknown explicit producer kinds also stay out of the user queue. Message text is never used to classify the source.

The slash `/quit` operation only detaches the phone's active runtime and preserves the Session. Archiving is a separate sidebar operation that calls the native Workspace archive RPC; a successful archive also detaches any local runtime for that Session.

Update (2026-10-23): `/quit` now cancels the Session's running turn through `session/cancel` before detaching. Detaching alone left the native turn running on the computer with no phone-visible handle: the phone could neither see the work nor stop it, while the run kept consuming the shared service and model quota. The success receipt is emitted before detach because the APP treats `runtime.offline` as cancelling that runtime's in-flight commands. If native cancellation fails, the runtime stays attached and the command returns a failure, so the phone keeps a handle instead of hiding a Session that is still working. This does not change archiving, browser visibility or the Session's durable history.

The Host discovers native Agents at startup and follows the ones already working (`running`). An idle Agent stays a catalog row: it occupies no online card and costs no per-Session follow, skills or model RPC until the browser starts new work in it or the app opens it. A Session that is already attached stays online after its turn finishes. Reconnection reconciles native membership before reopening Session follows, because following a cold ordinary Session can activate its Agent. Explicit `/quit` suppresses automatic attachment until new browser work starts in that instance (idle→running), the app reopens it, or its native instance is removed. Follow openings and app history synchronization replay the current assistant prefix so joining a browser turn midway preserves already-generated text.

Provider management retains the complete native home patch. Native DSH HMR applies it; Orbis waits until the live provider route/default descriptors match before reporting success. Managed keys are excluded from the persistent child environment and synchronized through the native credential API, whose values are resolved per model request. Existing environment overrides are not silently replaced: native refusal causes the provider transaction to roll back. Active browser-only sessions are checked as well as Orbis sessions before switching. The shared process is never killed to apply a provider change.

## Running checkpoint and bounded history

A bounded follow tail that omits the current turn's `turn/start` does not by itself make the live inventory incomplete. A successful follow reconstructs the full assistant prefix and applies later events in source order; only an actual source gap, failed reconciliation or replaced connection declares the source unavailable. Historical coverage and live inventory completeness are evaluated independently.

Runtime status and metadata are deduplicated by content, with an explicit announcement for a newly attached device. Catchup loads the requested history rather than repeatedly returning an unrelated tail; the command tree remains a bounded view. The source, checkpoint and queue rules are implemented in [dsh-web-runtime.ts](../../packages/host/src/dsh-web-runtime.ts), with regressions in [dsh-web-runtime.test.ts](../../packages/host/src/dsh-web-runtime.test.ts) and [dsh-web-history.test.ts](../../packages/host/src/dsh-web-history.test.ts). Ordinary outbound queues and stalled paths follow [ADR-0044](0044-bounded-codex-live-publish.md).

DSH-LIVE-01 (2026-11-06): when a follow opening confirms the same running turn but omits an observed, uncommitted assistant prefix, defer that opening and retain the verified text and chunk indices. The source check waits for a full prefix or authoritative completion/new-turn history; expiration permits another native check. A missing accumulator does not establish an empty live inventory or acknowledge a fresh checkpoint. Regressions cover continued chunks, complete-prefix replay, canonical handoff, new turns and retry after the recovery deadline. Evidence: [verification.json](../../.artifacts/backend-stream-fix-20261106/verification.json). Implementation and automated verification are complete; deployment and Android device acceptance remain pending.

DSH-HISTORY-01 (2026-11-06): durable-event and assistant-chunk gaps reopen the native follow. Only an opening snapshot already in flight shares its source check; a live subscription alone does not prove recovery is pending. Unverified chunks are withheld, replaced callbacks are fenced and a timed-out opening permits another check. Recovery does not resubmit prompts.

DSH-HISTORY-02: historical completeness follows the actual root-to-head parent chain and is recomputed after bounded reconnects and page merges. Catchup reads backward from each missing parent until the phone's branch is covered, rather than repeatedly loading the latest tail. A native page that makes no progress reports a retryable synchronization error.

DSH-HISTORY-03: prefix replay restores the native `activeAttempt.nextIndex`, because compacted prefix records do not determine the next live frame index. Snapshots without that field retain the replay-derived cursor. Implementation and regressions: [dsh-web-runtime.ts](../../packages/host/src/dsh-web-runtime.ts), [dsh-web-runtime.test.ts](../../packages/host/src/dsh-web-runtime.test.ts). Synthetic reproductions and automatic verification: [verification.json](../../.artifacts/dsh-history-stall-20261106/verification.json). Code and automatic verification are complete; no Host was deployed or restarted, and Android device acceptance remains pending. Apply through an updated Host, then verify new replies and reconnection in the same DSH Session on Android.
