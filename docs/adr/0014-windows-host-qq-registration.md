# Windows Host client and QQ mailbox registration

Status: accepted (2026-09-22).

The Relay operator controls whether new Hosts must verify a QQ mailbox. The persisted policy defaults to required; changing it requires the existing same-origin administrator session and CSRF token, and is audited. Public registration status reports the policy and SMTP availability.

The Windows client uses C++20, Qt 6.8 and QML. It owns its tray, settings, local activation storage and the lifecycle of a private Host child process. The TypeScript Host owns encryption, transport and Agent semantics; production runtime modules use generated `dist` files.

When verification is required, an opaque, short-lived challenge and an emailed, single-use code bind an `@qq.com` mailbox to the specific Host ID before credential issuance. When optional, a new Host can activate with its Host ID alone. Direct activation issues a random credential, is rate limited by source, and cannot replace an existing identity. The server stores credential hashes. Windows stores the issued credential using user-scoped DPAPI. Relay administrator and SMTP credentials remain server-side.

A verified Host credential authenticates exactly one Host ID and can issue pairing codes scoped to that Host. Device transport credentials inherit that scope. Relay rejects cross-Host routing and limits Host online/offline notices to relevant devices. Relay still receives only opaque session ciphertext; registration adds mailbox and credential records, not agent or conversation semantics.

SMTP is a server-side dependency: required verification without SMTP makes new registration unavailable; optional verification permits direct activation. Existing credentials remain valid when the policy changes. Production has no development-code endpoint. Code expiry, retry limits and request throttling protect mailbox verification, separately from paired runtime command authority.

The client reads the selected Relay's registration policy; an older Relay without that policy retains the QQ flow. Administrator-managed CLI provisioning remains a separate path. Registration state version 2 records whether an email was verified and reads version 1; after direct registration, rollback requires a Relay build that understands the new state. Protocol rollout follows [ADR-0064](0064-protocol-compatibility.md).

The UI follows the existing Orbis neumorphic surface tokens. A native QQuickPaintedItem provides soft outer shadows and genuinely clipped inner shadows with software rendering, including Windows Remote Desktop and non-integer display scaling. Focus, errors and state labels retain explicit colors and text.

## 2026-11-12: recoverable Host activation (HOST-ACT-01–07)

An explicit runtime `unauthorized` during startup or reconnect returns the desktop to registration. The rejected credential is removed from native secure storage off the UI thread; recovery retains the Relay endpoint, known mailbox, Host identity, keys and phone pairings. Network failures, protocol-version errors and administrator disablement preserve activation. Reinstalled and portable clients use the existing shared per-user credential store.

An existing verified registration recovers through its original mailbox, including when new computers may activate without email. Registration conflicts return an optional recovery hint without revealing the mailbox; an older Relay's generic conflict retains the mailbox recovery entry. A direct registration whose credential is lost requires an authenticated administrator reset. The existing console confirmation, same-origin session, CSRF and audit protect that reset. The registration remains visible with `activationResetAt`, its previous credential becomes unusable, and the next activation follows the current verification policy. Reset state stays within registration format 2; older loaders accept the additional field and continue rejecting the revoked credential.

Scenarios and assertions are in [desktop-runtime.test.ts](../../packages/host/src/desktop-runtime.test.ts), [HostActivationTest.cpp](../../packages/windows-host/src/tests/HostActivationTest.cpp), [registration.test.ts](../../packages/relay/src/registration.test.ts) and [admin.test.ts](../../packages/relay/src/admin.test.ts). ## 2026-11-12: Relay-scoped activation (HOST-ACT-08–12)

The selected Relay is the authority for authentication and registration policy. Cached activation enables a connection attempt; only that Relay's successful handshake means connected. Switching endpoints drains the previous runtime, selects the credential for the normalized endpoint and actual Host ID, then resumes a previously running Host. A new endpoint waits for activation. Registration, mailbox, challenge, pairing QR and delayed responses belong to the selected connection generation. Switching does not delete or reset server-side registration, and a refusal invalidates only the selected Relay's credential. Administrator disablement and network failure retain it.

The shared user credential directory keeps encrypted per-Relay/Host archives. The existing `activation.dat` remains the authoritative active slot in its released format. Selection archives that slot before atomically replacing it; a failed archive preserves the previous endpoint and credential. A released client's credential rotation is read from the active slot on return to the new client. Rejected credentials are removed from both the active slot and its archive. Secure-store selection and writes run on a serial background worker. Host keys and phone trust files remain unchanged; an independent Relay still needs its own phone transport pairing.

Scenarios: HOST-ACT-08 restores A/B credentials across switching and restart; 09 isolates rejection and mailbox recovery; 10 preserves the current activation when storage fails; 11 isolates Host identities and reads legacy credential rotations; 12 drains old authentication and ignores prior-visit policy responses. Implementation is in [CredentialStore.cpp](../../packages/windows-host/src/CredentialStore.cpp) and [HostController.cpp](../../packages/windows-host/src/HostController.cpp); regression assertions are in [HostActivationTest.cpp](../../packages/windows-host/src/tests/HostActivationTest.cpp). Automated results, original-behavior comparison and released native storage compatibility are retained in [.artifacts/relay-switch-activation-20261112](../../.artifacts/relay-switch-activation-20261112/). Publication, Windows installation and user acceptance remain pending.

## 2026-11-13: registration input ownership (HOST-ACT-13)

The mailbox field owns its editable draft. Shared Host status notifications, policy refreshes, busy transitions and code-request cooldowns preserve its text and selection. A change of Relay, Host identity or saved mailbox initializes the mailbox from that context and clears the previous verification code. ## 2026-11-13: refused mailbox recovery (HOST-ACT-14)

A mailbox verification that the Relay refuses as an existing registration ends mailbox recovery for that attempt instead of requesting the original mailbox again. The released Relay sends no recovery hint, so a Host first activated without a mailbox could not leave that prompt. The desktop names the administrator reset with the Host ID, keeps mailbox entry unless the Relay names administrator recovery, and discards the consumed code. A refused direct activation from a Relay without a hint offers both paths. Implementation is in [HostController.cpp](../../packages/windows-host/src/HostController.cpp); [HostActivationTest.cpp](../../packages/windows-host/src/tests/HostActivationTest.cpp) drives the actual request through a local Relay fixture for the released, mailbox and administrator responses. Original failure and fixed results are in [.artifacts/host-activation-loop-20261113](../../.artifacts/host-activation-loop-20261113/). Hosts already in this state recover through HOST-ACT-16 or an administrator reset.

## 2026-11-13: Host key recovery (HOST-ACT-15)

A Relay records a Host's long-term X25519 public key once: from an activation that carries it, or from the holder of a valid credential after connecting. A different key never replaces a recorded one, and an administrator reset removes it. A Host that still holds the matching private key replaces a lost credential without mailbox or operator: the Relay issues a single-use, two-minute ephemeral key, the Host returns `HMAC-SHA256(X25519, label|hostId|challengeId)`, and the Relay issues a new credential while keeping the mailbox, registration time and policy. The private key stays in the Host process; the desktop only relays the challenge and proof. Challenges are limited per source, not per Host, so knowing a Host ID cannot lock its owner out.

The desktop attempts recovery when it has no usable credential and the selected Relay advertises `hostKeyRecovery`: at launch, after a rejected credential, after an unreadable credential store and after a registration conflict. It tries once per loss and at most three times per run, so two copies of one identity cannot keep replacing each other's credential. A paused Host stays paused. Refusals are silent and leave the other activation paths unchanged. Released Relays advertise nothing and accept the extra activation field, so the desktop sends no recovery requests to them. Recorded keys survive a released Relay's load and rewrite; its rotations drop them until the next connection records them again.

## 2026-11-13: activation as a new computer (HOST-ACT-16)

When a Relay refuses to restore the Host ID, or a verified mailbox may be out of reach, the desktop offers activation as a new computer after confirmation. The current identity and its phone pairings move to `retired-identities/<hostId>-<time>/` in the Host state directory, a new identity keeps the computer name, and the new Host ID activates under the current policy like any new computer. Phones are added again. The old registration, credential archive and pairing records remain for an operator or a later restore. A running, connected or exiting Host cannot change identity.

## 2026-11-13: credential recovery ordering (HOST-ACT-17)

A runtime credential refusal persists the rejected credential before attempting key recovery. If the Relay's recovery policy arrives while secure storage is still busy, the completed write immediately retries the armed recovery for the same activation generation. A paused Host stays paused; a running Host resumes with the replacement credential and the selected Relay. The existing per-loss and per-run recovery limits still apply.

Implementation: [HostController.cpp](../../packages/windows-host/src/HostController.cpp) `invalidateActivation`. [HostActivationTest.cpp](../../packages/windows-host/src/tests/HostActivationTest.cpp) blocks the real secure-store worker until the policy response has arrived, then checks both paused and running recovery without a polling timer. It verifies the stored replacement and the actual bridge start's Relay and credential. The unchanged assertions fail on the original implementation in both states; fixed results and public deployment observations are retained in [.artifacts/relay-host-credential-alignment-20261113](../../.artifacts/relay-host-credential-alignment-20261113/). This adds no wire fields or storage format changes. Installation and user acceptance remain pending.
