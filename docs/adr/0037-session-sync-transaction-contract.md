# ADR-0037：会话同步的分布式事务契约

日期：2026-10-22

2026-10-22：[ADR-0038](0038-wire-payload-truncation.md) 处理本文未覆盖的另一类失败：单条 Entry 超过快照上限时同步必然失败。它属本文 §5 的"确定性失败"，但通过截断让该 target 不再必然失败。

Status: accepted（2026-10-22 实现 §1–§8：事务标识与去重、协调者回 `pending`、按阶段租约与到期 abort、投递进展回调、设备 `applied` 回执与 ack 租约、设备侧尝试层与会话层拆分、失败分类与目标级封锁。Host 侧改动需重启 Host 才生效）

关联：[ADR-0013](0013-bounded-session-sync-and-shared-tree-ingestion.md)、[ADR-0024](0024-recoverable-session-state-sync.md)、[ADR-0025](0025-native-history-authority-and-versioned-caches.md)、[ADR-0026](0026-host-selected-session-sync.md)、[ADR-0029](0029-session-read-operation-state-machine.md)、ADR-0035（待重建）、[ADR-0036](0036-sync-backpressure-is-not-failure.md)

## Context

现象：Host 持续返回 `session_sync_busy`；最新消息不再进入 APP；运行状态长期加载不出来；必须重开 APP 才恢复。

### 这次同步是什么

一次 `session.sync` 是三个独立进程之间的一次分布式事务，而不是一次函数调用。三方各持一部分状态与资源，任何一方都可能单独失败，而失败时另外两方不会自动知道：

| 参与者 | 持有 | 失败时实际发生什么 |
|---|---|---|
| 设备 | 本地缓存、`applied` 版本（ADR-0026）、界面状态 | 本地超时后自行判断失败，并把结论写进会话级字段 |
| Host（协调者，同时是资源所有者） | 活跃名额、字节预留、投递槽、任务记录 | 静默 `return` 或 300s 后过期；无法知道设备是否收到 |
| 后端（Pi / Codex / DSH） | 原生历史、快照生成能力 | 可能长时间不回应，Host 无从得知 |

### 契约应当包含什么，现状缺什么

分布式事务的契约不是可选的实现细节，缺少任何一条都会让某次事务停在未终止状态。逐条对照：

| 契约条款 | 本系统现状 | 违约后果 |
|---|---|---|
| 事务标识：一次逻辑事务只有一个稳定身份，参数不可变 | 有：`commandId`（设备归属）+ `syncId`（响应关联）（ADR-0013） | — |
| 协调者唯一：只有协调者判定结果并释放资源 | **缺**：Host 有协调者身份，但三个分支不宣布结果；设备反而自行判定失败 | 一侧已判定失败，另一侧仍合法占用名额与预留 |
| 无未终止等待：受理后必须在有限时间内把终态送达双方 | **缺**：`SessionSyncTasks.request` 三个分支直接 `return`，不发任何响应 | 设备无法区分"在处理"与"已丢弃"，只能靠本地超时猜 |
| COMMIT 由参与者确认：发送侧写完字节不等于对方已提交 | **缺**：`delivered` 只表示字节写进 socket，协议明确没有 ACK | Host 无法区分"到达"与"在途"，丢帧后不会重发 |
| 持有资源的未终止事务不得长期存在 | **缺**：`processing` 只有 300s，`sending` 没有任何到期判定 | 资源被占着，而设备早已放弃 |
| in-doubt 是允许的中间态，但必须由协调者消解 | **缺**：in-doubt 被设备直接当成 aborted，并写成持久状态 | 一次失败 = 该会话长期停更 |
| 幂等重放：同标识重放不产生第二份工作，且结果可观测 | 部分：同 `commandId` 会去重，但去重时静默 | "幂等但不可观测"，重试变成盲等 |
| 失败只影响这次事务，不写成事务外的长期状态 | **违反**：preview 失败直接写 `sessionSyncFailures`，而该字段同时是"是否发送请求"的闸门 | 一次失败停掉整个会话 |

做对的一半在数据侧：原子写入、归属校验、隔离（旧响应不得改 head）、持久化与崩溃恢复，按数据库事务标准实现（ADR-0013 §2、ADR-0024、ADR-0025）。缺的一半全在协调侧：作废判定、终态送达、提交确认、失败的持久性边界。

### 历史成因（两次方向相反的故障）

- 2026-09-21 之前：APP 等 8 秒即放弃并换新 ID 重请求，Host 不取消已排队响应 → 重复整图、GB 级队列（ADR-0013 Context）。
- ADR-0013 的处置：给每次同步稳定身份、重试复用同一 ID、Host 只回请求设备、队列设上界。它解决了"放弃太早"，但把重复请求设计成静默去重，这正是"终态送达"缺失的来源。
- 2026-09-23 起：为阻止失败后随事件重复请求，引入 `sessionSyncFailures` 作为闸门；后来该闸门接入 preview 调度 → 反向故障。

两次都不是"用了事务"的错误，而是事务只实现了开始、没有实现结束。

## Decision

以下每条都是这次分布式事务的契约条款。违背任意一条，都会让某次事务停在未终止状态，而设备侧无法自行恢复。

### §1 事务标识与不可变参数（已实现，固化）

同一 `commandId` 的参数（runtime、sessionId、syncId、range、边界、`maxEntries`、`knownState`）不可变；变化一律 `session_sync_id_conflict`。同一 `syncId` 不得属于两个事务。重试复用同一标识（ADR-0013），但必须可观测（见 §3）。

### §2 协调者唯一：作废只能由资源所有者判定，租约必须通告

名额、预留、投递槽的所有者是 Host，也就是这次事务的协调者，因此：

- 只有 Host 能判定一次事务作废并释放资源。设备可以报告本地结果，但不得宣告事务失败，更不得据此写会话级状态。
- Host 的租约随响应下发：`pending` 与 `snapshot` 都携带 `leaseMs`。设备本地兜底超时必须 ≥ `leaseMs` + 传输余量，并且不得使用硬编码常量（设备 150s、Host 300s 是两个互不知情的数字）。
- 租约续期只能基于进展事实：后端回报阶段进展、字节写出、设备确认。没有进展就不续期。这是区分"慢"与"死"的唯一可靠判据，也是固定 20 秒超时被否决的原因（ADR-0036 §7）。
- 按阶段取值：`processing` 没有中间进展通道，租约 120s；`sending` 每写出一片都算进展，租约 60s。
- 租约到期：abort，回 `session_sync_lease_expired`，同时释放名额与预留。

### §3 无未终止等待：终态必须送达

受理之后，Host 对同一事务的任何询问都必须回三者之一，禁止直接 `return`：

| 情形 | 现在 | 契约要求 |
|---|---|---|
| 任务在 `queued`/`processing`/`sending` | 静默 | 回 `session_sync_pending`（带阶段与 `leaseMs`） |
| `delivered` 且未到重派间隔 | 静默 | 回 `committed`（已 sent）或 `pending`（重派中） |
| 失败或尝试超限 | 回 `retry_exhausted` | 保持码不变，归类为 `aborted` |

设备收到 `pending` 时重置本地等待窗口，因此不再需要靠猜；只有收到 `aborted` 才进入重试或停止。重置有上限（连续 `MAX_PENDING_NOTICES` 次），避免协调者永久 pending 时设备无限等待。

### §4 COMMIT 由参与者确认

区分两个事实：`sent` 是 Host 把字节写完，`applied` 是设备完成 SQLite 事务并推进本地已应用版本（ADR-0026）。

设备在 applied 或明确 rejected 之后回 `session.snapshot.ack {syncId, result}`。Host 以 ack 作为 `committed` 的唯一依据；没有 ack 时会话按 §2 的 ack 租约 abort（`session_sync_ack_timeout`），允许重试。

ack 丢失必须是安全方向：设备已 applied 而 Host abort → 设备重试携带 `knownState` → Host 回 `unchanged`（ADR-0026 已具备），不产生重复内容也不回退视图。

兼容：不发送 ack 的设备由 Host 视为 sent 即 committed，ack 租约只对**曾经回过执的设备**生效。

### §5 失败是尝试状态，不是会话状态

事务结果分两层存储，职责不得混用：

- 尝试层（短生命周期，驱动重试节奏）：最近一次失败码、下一次允许重试的时间、连续失败计数，以及"确定性失败挡住的 target"集合。
- 会话层（仅用于显示）：最近一次失败原因文本。

禁止会话层字段参与"是否发送请求"的判定。`sessionSyncFailures` 当前的闸门职责必须迁出（ADR-0036 §8 的 10 秒冷却是过渡措施）。

确定性失败（单条 Entry 超 `SESSION_SYNC_MAX_BYTES`、参数非法、版本不兼容、命令不支持）允许长期不重试，但必须由失败类别显式表达，且只影响对应目标（例如"这个 target 无法同步"），不得连带停止该会话的新内容同步。

### §6 幂等重放

- 同标识重放不产生第二份工作（已实现），但必须可观测（§3）。
- 换标识重试必须发生在旧事务 abort 之后；新事务不得复用旧 `syncId`。
- 节奏由失败类别决定：`pending` → 继续等待，不重发；`aborted(retryable)` → 退避重试；`aborted(deterministic)` → 停止并向用户显示原因，同时保留其它目标（新回合、新页）的同步能力。

### §7 资源生命周期受租约约束

名额、预留、投递槽的解绑必须有到期路径：

- `processing`：由后端回报进展续期，无进展按 §2 到期。
- `sending`：以"字节是否前进"为进展判据（`msg` 通道目前没有排队过久检查，`bulk` 有 `onBulkQueuedTooLong`），无进展按租约 abort。
- abort 必须同时释放名额与预留，不得只删记录。

### §8 与收敛模型的关系

`preview` 的语义是"追平到 head"，将来可以改为 level-triggered（设备声明已应用版本，Host 直接推增量或 `unchanged`），从而减少事务簿记。本 ADR 不以此为前提：§1–§7 补齐后，事务模型已经具备可恢复性；收敛化是可选优化，不是解决本类问题的必要条件。

## Consequences

### 只实现一部分的结果

| 只做 | 结果 |
|---|---|
| 只加截止时间（不做 §3） | 到期才回包，等待期间设备仍在猜；慢后端被误杀（已验证过，见 ADR-0036 §7） |
| 只做 §3（回 `pending`） | 设备不再盲重试，但资源仍可能被长期占用（§2/§7 缺失） |
| 只做 §2（租约）不做 §4 | "已送达"仍无确认，丢包只能靠重试发现 |
| 只做 §5（拆状态） | 设备不再永久停更（ADR-0036 已达成），但每次失败后仍是盲重试 |
| 做 §2/§3/§4 但保留会话级闸门 | 事务能结束，但一次确定性失败仍会停掉整个会话的更新 |

### 顺序与成本

1. §3（Host 三个静默分支回 `pending`）：一个响应码，成本最低，单独就能让设备不再靠猜。**已实现**
2. §2 + §7（租约与进展判定，含 `sending` 的字节进展）：Host 侧状态机改动。**已实现**
3. §5（设备侧把尝试状态与会话状态拆开）。**已实现**：`sessionSyncBlockedTargets` 只挡确定性失败的目标，`sessionSyncFailures` 退回纯显示。
4. §4（`session.snapshot.ack`）：协议新增消息，需同时改 Host、设备与协议校验。**已实现**

### 其它

- 每个租约值与续期判据都必须可观测（日志字段：阶段、进展来源、租约剩余、abort 原因），否则下次仍然无法从现场判断是慢还是死。
- 本 ADR 的实现都在 Host/协议侧，需要重新打包并重启 Host 才生效；重启会中断当前会话，须单独授权。

## 验证

- 状态机测试：受理 → `pending` → abort → 重试 → `committed`；ack 丢失后重试得到 `unchanged`。
- 不得回归 ADR-0013 的验收条款：延迟超窗、响应丢失、换路、离线设备、多设备、多 Runtime 下不形成重复响应积压；当前聊天能完成或显示可恢复错误。
- 明确禁止的回归：任何路径不得让 `sessionSyncFailures` 之类的会话级字段阻止新事务受理。
