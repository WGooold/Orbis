# 写入层切片：让水位重新成为节拍器

**Status:** accepted

出站多路复用器按水位放行 `bulk`、让
`ctl` / `msg` 插队，但它的水位判据是**每次取帧之前查一次 socket 积压**——于是「一次写入有多大」
直接决定它是否有效。本 ADR 决定在**写入 socket 之前**把已封好的信封切成小片交付（票 03 的
「方案 B」），而不是去改传输层的片大小。

## Context

### 水位被一次 1.34 MB 的写入打穿

一条 `bin` 信封的 `ct` 约 1.34 MB（1 MiB 载荷 + base64 的 1.33×）。放一片进 socket，
`bufferedAmount` 立刻从 0 跳到 1.34 MB，把 `bulk`（64 KiB）与 `msg`（1 MiB）两个水位**同时**
跨过，闸门关死到链路把这一片排空为止。

仓库里有一段真实运行输出（当时由本地部署脚本写进 `data/relay-cicd.log`；**那条本地链路已删除，
现在部署在 GitHub Actions 里，对应输出在 Actions 页面**）：

```json
{"event":"relay.bulk.queued","queuedMs":1002,"queuedBytes":16781827,"bufferedAmount":1398495}
```

`bufferedAmount` = 1,398,495 ≈ 与估算的信封大小只差 243 字节——「一次写入 = 一帧 = 1.34 MB」
由此得到实测确认；`queuedMs` = 1002 说明有一片在队列里等了整整一秒，而这一秒里 `msg` 会被它挡住
（只有 `ctl` 能绕过水位）。弱链路上这条延迟是秒级，说明仅给逻辑 channel 分开计数不足以隔离控制面延迟。

### 传输层片大小方案的取舍

`ARTIFACT_CHUNK_BYTES` 同时定义三件事，改它就会把「延迟重排」变成「系统性丢片」：

- **窗口按片数定义**：`ARTIFACT_WINDOW_SIZE = 16` → 片改小，在途字节同比例变小；**（该常数已在 [ADR-0009](./0009-remove-computer-to-phone-push.md) 中删除。接收方驱动的 pull 窗口按字节定义——今天是 Android `PullScheduler` 的 1–8 MiB——所以片改小只让 `artifact.read` 请求数上升，在途字节不再同比例下降；本 ADR 拒绝方案 A 的其余两条理由仍然成立。）**
- **中继护栏由这两个常量算出**：片降到 32 KiB，护栏会从 64 MiB 掉到 2 MiB，而手机的 pull 窗口是
  1–8 MiB（初始 4 MiB）——**护栏小于在途量 → 中继持续拒绝合法分片**；
- **pull 请求数**随片变小上升（每片一条 `artifact.read`）。

而且它对 `msg` 完全无效：`msg` 里最大的是会话快照（可达数 MB），不是 artifact 分片。

## Decision

### 出站调度与背压边界

每条路径各持一个 `OutboundChannelMux`，通道内 FIFO，基础优先级为 `ctl > msg > bulk`；`ctl` 可越过水位，`msg` / `bulk` 按底层 backlog 放行。水位约束已写入链路的排队延迟，应用层队列仍须有界。Host 封帧前执行有界准入，已封装密文按所属连接及同通道 FIFO 交付。普通队列超预算、长期停滞与路径退休按 [ADR-0044](0044-bounded-codex-live-publish.md)，接收消费队列按 [ADR-0040](0040-bounded-inbound-delivery.md) 处理。原生五流及扩展通道的认证、预算与优先级见 [ADR-0065](0065-native-quic-relay-transport.md)。

**在写入边界切片：切的是已封好的 `ct`，片是 `v2.frame` 的一种新 `hdr.k`。**

- **片格式**：`hdr.k = "piece"`，照旧包在 `{type:"v2.frame", …}` 里。`hdr` 带 `to` / `ch`
  （中继路由与排队用）、`ik` / `n`（**原信封**的 kind 与序号，重组时原样放回）、`mid`（同一条
  消息的片共用）与 `idx` / `last`（完整性判据）。片里的 `ct` 是原信封 `ct` 的一截。
- **切 `ct` 而不是整条 JSON**：`ct` 是 base64url（纯 ASCII、不含引号），片载荷在 JSON 里不需要
  任何转义，重组就是字符串拼接。
- **中继零改动**：它照旧只按 `hdr.to` 路由、按 `hdr.ch` 排队，**不重组**也不需要看懂 `ct`；
  半截消息只在两个端点存在。中继因此保持纯 JSON、无状态。
- **小消息不切**（≤ 8 KiB 原样发），否则每条控制帧都要多背一个片头。
- **重组有界且会超时**：并发条数与总字节都有上限，超时/越界丢弃整条。片层**不判合法性**——
  拼出来的信封照旧过 `E2eChannel.open()`；丢了 `ctl` / `msg` 的整条消息，接收侧的序号不推进，
  后续按 [ADR-0011](0011-nonce-slot-and-high-watermark.md) 的已认证高水位接收；会话状态缺口由 source 版本与同步恢复处理。
- **写被拒时留在队首重试**，而不是丢弃。这一条只有在片足够小之后才真的可执行（1.34 MB 的写入
  被拒后缓冲区只会更满）。切片限制单次写入量，缓冲区满时稍后重试；重试耗尽才判那条路径失效。

### 片大小 8 KiB 的判据

它不是一个必须拍定的常量，而是由两条约束夹出来的：

```
上界（延迟）：一件的传输时间 ≪ 地板（= 内核缓冲的传输时间 + BDP）
              并且 件 ≤ 水位            ← 否则一件仍会被闸门整件放过
下界（开销）：片头开销 ≤ 1%
```

按 `地板 ≈ 内核缓冲` 估：1 Mbit/s（内核 64 KB，地板 ~500 ms）→ 件 ≤ 6.4 KB；5 Mbit/s → ≤ 32 KB；
50 Mbit/s → ≤ 410 KB。取 **8 KiB** 把延迟项压到地板的 1/10 量级（1 Mbit/s：65 ms vs 500 ms）。

片头开销是这条判据里唯一没达成的部分：票 03 按「片头 ~16 B」估算（那是二进制片头的量级），
而本实现用 JSON 片头（约 160 B），8 KiB 片上约 2%，不是 1%。**这是刻意接受的**：二进制片头要中继
解析二进制帧，而中继刚刚因为 [ADR-0009](./0009-remove-computer-to-phone-push.md) 变成纯 JSON
路由。要重新评估就改 `PIECE_MAX_CT_CHARS` 一个常量，判据两条都在上面。

### 2026-10-23 重组并发调整

Host 与 Android 同时重组的消息条数由 4 提到 16，以容纳四个活动同步响应与同时到达的文件分片、状态响应（ADR-0013 §6）。总密文字符预算保持 32 MiB、单片保持 8 KiB、重组期限保持 60 秒。出站 `msg` / `bulk` 水位保持 64 KiB，避免提高同步并发时增加 `ctl` 的线路排队时间。

## Consequences

- **延迟上界从「一整条信封」变成「水位 + 一件」**：1 Mbit/s 上 0.6 s 而不是 11 s；`ctl` / `msg`
  的等待不再由对端一次读盘的量决定。
- **吞吐不再由节拍封顶**：水位 / 节拍的上界从 6.4 MiB/s（10 ms）抬到 64 MiB/s（1 ms），
  代价只是「有帧被水位挡住时」每秒多 1000 次定时器唤醒。这条是复核阶段才发现的——切片把
  「一次交付多大」压下去了，却让**节拍**变成吞吐的瓶颈，见下面的「交付的节拍」。
- 中继不需要重组、不需要新状态，`muxChannelOfMessage` 与路由分支都不用改——片和普通帧走同一条路。
- 发送被拒时先重试，重试耗尽才判路径失效。
- 新增一个有界的内存面（组装的半截消息），上限是 `PIECE_REASSEMBLY_MAX_*`；新增一种线上帧种类，
  线路格式按 ADR-0064 保持已部署端兼容。
- 传输层片大小（= pull 请求粒度 = 窗口粒度）与「一次交付给 socket 的量」彻底解耦：以后要在两者
  之间做取舍，各自独立调整即可。

### 交付节拍与吞吐

水位只决定「一次交付多少」，**只有节拍决定吞吐**：交付完一个水位之后必须等链路消化才能再交付，
而这个「等」的长度就是节拍。于是缺省值本身就给出一个硬上界：

```
吞吐上界 = 水位 / 节拍 = 64 KiB / 10 ms = 6.4 MiB/s（≈54 Mbit/s）
```

这个上界是**复核时实测出来的**，不是推理：切片之后一个千兆局域网上的下载吞吐从 66.7 MiB/s
掉到 **6.40 MiB/s**；只把节拍改成 1 ms 就立刻回到 **63.98 MiB/s**——归因由此坐实。1 / 5 /
50 Mbit/s 三条链路上吞吐没有变化（瓶颈在链路本身），所以这个洞**只在快链路上暴露**，而
50 Mbit/s 正好卡在这条线上。另外 `notifyDrained()` 全仓库没有任何生产调用方，所以那时唯一的
推进者就是那个 10 ms 定时器。

因此把「等」拆成两种（`outbound-mux.ts` 的 `DEFAULT_DRAIN_POLL_INTERVAL_MS` = 1 ms）：

- **被水位挡住 → 1 ms 复查。** 链路正在正常工作，越早复查越不容易空转；代价是只在这段时间里
  每秒多 1000 次定时器唤醒（队列空或链路通畅时一次都没有）。节拍的选择只看这一轮的**停止原因**，
  所以定时器必须在 `#pump` 的循环之后才排。
- **写被拒 → 仍是 `DEFAULT_PUMP_INTERVAL_MS` = 10 ms。** 那是对端有问题，慢一点重试正好
  （重试次数本来就只有 5 次）。

**残余上界 64 MiB/s（≈537 Mbit/s）。这是权宜，不是终点**：干净的做法是让传输在消化时主动
通知（例如 `ws` 的 `send(data, cb)` 写出回调），那需要一条从各条出口反向回到多路复用器的通道。**真有 ≥512 Mbit/s 的链路时先做
那件事，而不是把这个数再调小**——定时器精度与唤醒开销都会开始咬人。

顺带把 `msg` 的水位从 1 MiB 收到与 `bulk` 相同（`DEFAULT_MSG_LOW_WATER_BYTES`）：它原来的理由
（「会话快照好几 MB，水位太紧会把它压住」）在切片之后不成立——一条消息已经是 8 KiB 的片，
水位与「一次交付多大」的关系反过来了。而**水位就是「一条控制帧前面最多能有多少字节」**，
1 MiB 的 `msg` 水位意味着任何一条大 `msg` 都能把 socket 积压抬到 1 MB，其后的 `ctl` / `msg`
都要等 1 MB / 带宽。实测（5 Mbit/s，每 5 s 一条 1 MiB `msg`）：`ctl` 的 P95 从 **1608 ms** 降到
**112 ms**。`msg` 相对 `bulk` 的优先级没有变（`#pump` 里先取 `msg`），所以两者水位相同也不会
互相饿死。

**这两条只写在文档里，没有测试钉住**——刻意的：它们的取值是「可由判据推导、并可由实测微调」
的参数，钉死一个数只会让下一次调整多一道与行为无关的假红。要用数复核就跑
本地节拍探针（历史诊断脚本，未随源码发布）（把节拍显式调回 10 ms，就能看见 6.4 MiB/s
的旧上界；它同时给出 ctl / msg 的 P50 与 P95）。
