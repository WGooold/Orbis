# ADR-0013 · 有界 Session 同步与统一 Session Tree 写入

日期：2026-09-21

Status: accepted（设计已采纳；实施状态以关联 tickets 为准）

关联：早期内部设计记录（不包含在公开仓库中）、早期内部设计记录（不包含在公开仓库中）。

取代旧 早期内部设计记录（不包含在公开仓库中） 和 早期内部设计记录（不包含在公开仓库中） 中“preview/history 不落盘、catchup 是唯一远程 Entry 写入者”的决定。保留 canonical Entry 身份、分支按 parent 关系查询、实时显示与缓存分离的约束。

## Context

`preview`、`history`、`catchup` 是同一个 `session.sync` 命令的范围参数，均返回 `session.snapshot` 和同一种 `RemoteSessionEntry`。它们的显示目的不同，不代表节点内容不同。目前 preview/history 显示后丢弃，catchup 需要再次下载相同节点。

与此同时，Codex 忽略范围参数，反复发送整份 Entry 图；APP 等待 8 秒后删除请求归属并重新生成请求；Host 已排队的响应不随之取消。慢链路下可能形成“超时、重复整图、排队增长、迟到响应被拒”的循环。2026-09-19 已观察到 GB 级应用队列；2026-09-21 仅 Codex 异常的现场尚未量出响应耗时，不能把两次现场的初始原因等同。

直接允许三个处理分支各自写库不安全：当前 `mode=replace` 被当作覆盖已有 Entry 的权限，数据库写入失败还会触发整 Session 清理；观察到一个末尾节点也不证明它到 root 的祖先已经齐全。Codex 重放还会用当前时间重新生成 Entry 时间戳，必须先消除同一 Entry 在不同读取中的不稳定内容。

## Decision

### 1. 同一范围接口，两个后端遵守相同契约

- `preview` 返回目标分支末尾的一页，`mode=replace`；`history` 返回 `beforeEntryId` 之前的一页，`mode=prepend`；`catchup` 从已知连续位置向本轮固定目标前进，通常 `mode=append`，无共同前缀时可返回 `replace`。
- 返回原请求 `syncId`、实际范围与目标，正确计算 `hasOlder`、`complete`、`rangeStatus`。`complete` 只描述本次请求范围，不能直接认定本地整条分支完整。
- 同时限制 Entry 数和完整响应的 UTF-8 字节数（含 timing 等元数据），不同后端复用同一个规范化 Entry 分页算法。正常页预算初始为 256 KiB；一个不可拆分 Entry 可单独占一页，但完整响应硬上限为 1 MiB。预算计入响应外壳并保留传输外壳余量；Host 的队列预算另按加密、base64、切片后的估算字节计量。
- 单 Entry 加必要元数据仍超过硬上限时，返回带请求关联的明确错误；不截断、不改写 Entry、不跳过该节点后假报完成。大 Entry 外置附件属于后续独立设计，不在本轮悄悄加入。
- 同一稳定 Entry 的 ID、parent、type、timestamp、data 在 preview/history/catchup、重试和重放间必须一致。未完成的实时 item 留在实时显示路径；完成后才进入 canonical Entry。Codex 缺失源时间时采用明确、确定的缺省值，禁止以请求/重放时间冒充源时间。

02 票的具体约定：缺失 `range` 明确报 `session_sync_range_required`，不保留不限量返回。当前 Codex ThreadItem 不提供稳定的 item 时间，canonical Entry 的时间固定为 `1970-01-01T00:00:00.000Z`，内嵌 message 时间为 `0`，实时显示事件仍用接收时间；工具结果内的 JSON 对象按键排序，避免属性顺序制造正文差异。并发 item 按源 item 的开始顺序提交完成结果，未完成前缀不允许后续节点越过。带 messageId 的 timing 跟随所属页，未带锚点的 timing 计入每页元数据预算，超限明确失败。

rollout 选择优先使用 app-server 明确返回的文件路径，并核对 `session_meta.id`；没有路径时，候选文件必须按内部 Session 身份唯一匹配。多个有效候选报 `rollout_ambiguous`，不按长度、修改时间或目录顺序猜测；中间损坏的记录报错，正在追加的末尾半行不参与回放。

### 2. 三类响应共用一个事务写入入口

- preview/history/catchup 中通过归属和结构校验的完整 Entry 都可以持久化；三个 UI 分支不得直接各自更新数据库。
- canonical 身份为当前配对 Host/设备缓存命名空间下的 `(sessionId, entryId)`。同 ID 同内容是幂等；不同 parent、type、timestamp 或 data 是冲突，整批回滚，保留已提交数据并给出可恢复错误。
- `replace/append/prepend` 只控制范围和显示合并，**不是覆盖 canonical 节点或删除其他分支的权限**。取消基于 `mode=replace` 的覆盖捷径；普通同步失败不得清整个 Session。
- 一个事务包含节点校验、写入、覆盖范围/连续性更新，提交前后检查请求归属。归属至少包括设备、连接代次、Runtime、Session、分支/视图代次、逻辑任务、range 和分页边界。仅 `runtime+session+range` 相同不足以接受响应。
- 缺失 parent 允许作为已知不完整的缓存片段保存；禁止自环、已可证明的 parent 循环、同一批次重复 ID 内容冲突。后续补 parent 时仍检查与已有节点构成的循环。
- timing 是独立元数据：缺失结束信息可单调补全，不能让旧响应回退已知完成信息，也不能靠合并时序改写 Entry。冲突策略须有测试。
- 内存中的 canonical graph 与 SQLite 使用相同合并规则；实时 tail 仍是独立显示覆盖层，不能因较早的 preview/history 到达而丢失或倒退。

### 3. 节点存在、连续覆盖、当前显示位置分开记录

- “已保存 Entry 8～10”不等于“已保存 root～10”。显示 leaf、目标 leaf 和经过 parent 关系验证的持久同步进度必须分开。
- 只有数据库确认所需祖先链完整且事务成功，才推进连续进度。不能仅信 `snapshot.complete`、`cursor.leafId` 或取本页最后一个 ID。
- preview/history 补齐缺口后也可由统一入口证明连续性并推进进度；进度推进取决于数据事实，不取决于请求名称。
- 读取首屏和历史页优先使用本地覆盖；catchup 也必须利用已保存片段缩小缺失范围，而不只是写入时去重。
- 示例：已保存 1～3、8～10 时，catchup 只补 4～7；若 history 已补 5～7，则只补 4。可沿目标的已缓存后缀找到缺失 parent，利用现有 `knownLeafId/targetLeafId` 请求缺口，不要求上传全部已知 ID。
- 请求缺口的目标可以是当前分支的祖先；它与用户正在查看的 leaf 分开。仅凭两者不相等不能拒绝合法补洞，也不能拿补洞目标倒退实时 leaf。分支切换通过任务所属代次判断，正常同分支 tail 增长不反复废弃固定目标任务。
- 数据库升级保留已有 Entry 和配对数据；旧 cursor 不能未经验证直接迁移成“连续已完成”。本地内存中的有界窗口也不能代表磁盘完整覆盖。
- 已落盘的 Codex Entry 可能含旧实现生成的重放时间。源表示修正必须有显式、可回滚的迁移规则：只对已确认属于旧 Codex 表示的字段做确定性转换，并保留旧数据；无法证明等价时隔离旧表示并报告冲突，不能把“忽略时间差异”变成所有 Entry 的冲突豁免。该迁移通过后才能启用新写入入口。

### 4. APP 的同步任务有稳定归属和有限重试

- 一个逻辑任务对应设备/连接代次、Runtime、Session、分支代次、range、固定 target 和起止边界；相同任务最多一个在途响应。
- 短等待窗口到期表示“同步较慢”，不删除仍有效的请求归属，不每 8 秒换新 ID 重新下载。重试复用逻辑任务和关联 ID；新页、用户显式重试或目标切换才创建新任务。
- 使用有上限的退避重试和总等待窗口。达到上限后停止自动制造请求，保留已有聊天并显示可重试状态；保留有界的迟到响应关联，使仍属当前任务的有效响应能够完成恢复。
- 成功的 `command.result` 只证明命令处理，不能当作快照送达。真正完成依据是响应被接收并提交；重试计数和每页发送时间必须独立更新。
- 切换 Session/分支、连接代次改变或任务被明确取代时，取消本地后续调度；旧响应不得污染新视图、缓存或同步进度。后台同步要有并发上限，用户当前首屏和主动历史请求优先。

### 5. Host 在封帧之前去重和背压

- Host 为同步请求记录设备归属，将 `session.snapshot` 定向返回请求设备；不向所有已配对设备广播请求响应，也不主动广播无人请求的整图。
- 重复请求在后端处理中、响应等待发送或该响应仍在发送队列中时合并，不重复生成或加密大响应。请求键包括设备、Runtime、Session、任务 ID 和不可变范围参数；同 ID 不同参数明确拒绝。
- 已发送之后的重试允许重传以恢复丢失响应，但遵守退避、有限保留和总队列上限；“交给 socket”不等于“APP 收到”。记录有界，连接重建及设备撤销清理旧任务。
- 每设备限制等待任务数和同步响应字节数，在加密/切片前预留预算。没有可用路径或队列超限时返回关联的可重试忙/失败状态，不无限排队。前台请求优先于后台 catchup，且不饿死后台。
- 不删除、重排同一消息的已封装分片来取消任务，不改变加密 nonce 与 channel 顺序规则。Relay 保持只转发不透明密文，不参与 Session 语义。
- 记录事件类型、请求 ID、范围、Entry 数、明文字节、队列字节、排队/发送时间和重试数，日志不记录聊天正文。这样可以区分后端计算、Host 排队和实际链路延迟。

## Consequences

首屏和历史下载可以补充持久缓存，后续追赶复用这些数据，减少重复传输。代价是需要显式表示不完整缓存片段与连续覆盖，并统一处理写入冲突；不能依赖三个显示路径各自“知道自己在做什么”。

首屏不等待完整树或后台同步。一个有界页面先完成统一校验和事务，再按其显示用途投影；数据库失败保留既有内容并显示错误，不继续提交未经确认的 canonical 状态。

本 ADR 不新增三套同步接口，不改 Relay 业务职责，不把提高超时常量当作修复，不顺带优化 thread/list 探询。rollout 多文件选择只在影响 canonical 身份/历史完整性的证据确认后按对应 ticket 处理，不用“取最大文件”猜权威来源。

如实施需要改变线上 schema，遵循 ADR-0008 同步升级与硬版本门槛；Protocol/Relay 改动遵循仓库 CI 部署入口。设计偏离、预算变化或新增功能必须先更新 ADR 和 ticket，不能只在代码中扩大范围。

## Verification

- 三种响应乱序、重复、交叠，最终节点集合和 parent 关系一致；跨分支共同前缀只存一份。
- `replace` 不覆盖冲突节点；失败整批回滚，旧树、进度和配对数据保留；迟到旧会话/旧分支响应无法写入。
- preview 末尾页落盘不跳过前面的缺口；补齐后自动连接，进度正确。重启后继续补缺失范围，网络确实少传已缓存片段。
- 大历史、多字节文本、大 timing、单个超大 Entry 下字节预算生效，两后端 range 语义相同。
- 延迟超过原 8 秒窗口、响应丢失、换路、离线设备、多设备和多个 Runtime 下，不形成重复响应积压；队列有明确上界或回落，当前聊天能完成或显示可恢复错误。
- 使用真实加密/切片/接收处理的有界慢链路回归，并验证数据库、reducer 与实时 tail；除单元测试外保留 Android SQLite 事务验证和实际 APP 加载验证记录。
