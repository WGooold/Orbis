## Context

2026-10-10：[ADR-0026](0026-host-selected-session-sync.md) 将 preview 的固定 tail 改为源端根据 APP 已应用基线选择 unchanged、state、delta 或恢复 snapshot；本 ADR 的历史分页、预算、事务、归属和背压要求继续有效。

`preview`、`history`、`catchup` 是同一个 `session.sync` 命令的范围参数，均返回 `session.snapshot` 和同一种 `RemoteSessionEntry`。它们的显示目的不同，不代表节点内容不同。目前 preview/history 显示后丢弃，catchup 需要再次下载相同节点。

与此同时，Codex 忽略范围参数，反复发送整份 Entry 图；APP 等待 8 秒后删除请求归属并重新生成请求；Host 已排队的响应不随之取消。慢链路下可能形成“超时、重复整图、排队增长、迟到响应被拒”的循环。2026-09-19 已观察到 GB 级应用队列；2026-09-21 仅 Codex 异常的现场尚未量出响应耗时，不能把两次现场的初始原因等同。

直接允许三个处理分支各自写库不安全：当前 `mode=replace` 被当作覆盖已有 Entry 的权限，数据库写入失败还会触发整 Session 清理；观察到一个末尾节点也不证明它到 root 的祖先已经齐全。Codex 重放还会用当前时间重新生成 Entry 时间戳，同一 Entry 在不同读取中仍有内容不稳定的问题。

## Decision

### 1. 同一范围接口，两个后端遵守相同契约

各后端共用范围接口、分页预算与确定性 Entry 投影，响应携带原请求身份和实际范围。

- `preview` 返回目标末页，`history` 返回指定边界之前的一页，`catchup` 补齐固定目标；`replace/append/prepend` 表达合并方式。
- `complete` 表示所请求范围的完成情况；连续历史覆盖由持久化入口核验。
- 分页同时核算 Entry 数和完整响应字节，超限返回关联错误；元数据与传输开销计入各自预算。
- Entry 的身份和内容由源事实确定，实时 item 完成后进入 canonical；源时间缺失时使用确定的缺省值。
- 原生日志按内部 Session 身份选择，并对歧义或损坏返回明确错误。

初始页预算为 256 KiB、完整响应硬上限为 1 MiB，后续容量见 §6。Codex 缺失源时间时，Entry 使用 `1970-01-01T00:00:00.000Z`、内嵌消息使用 `0`；实时显示使用接收时间。结果 JSON 按键排序，完成结果按源 item 顺序提交。

### 2. 三类响应共用一个事务写入入口

preview、history 与 catchup 统一经过归属、结构和源版本校验，在同一事务中提交节点与覆盖事实；内存图和 SQLite 使用相同合并规则。

canonical 身份为配对缓存命名空间内的 `(sessionId, entryId)`。重复内容幂等，冲突整批回滚并保留已提交数据；图结构验证覆盖循环与重复身份冲突。缺失 parent 的片段保留为部分覆盖，timing 按事实单调补全。实时 tail 保持独立显示归属。

### 3. 节点存在、连续覆盖、当前显示位置分开记录

分别维护节点存在、经过 parent 验证的连续覆盖和当前显示位置。统一写入入口在祖先链完整且事务提交后推进覆盖，所有同步方式共享这一事实。

首屏与历史优先使用本地覆盖，catchup 利用已有片段缩小缺口并保持固定目标。分支切换按任务代次处理；数据库迁移保留已有数据，以可核验、可回滚的转换修正旧表示。

### 4. APP 的同步任务有稳定归属和有限重试

同步任务绑定稳定身份、来源代次和固定范围，重试复用原归属并受退避、租约和预算约束。响应接收并提交后完成任务，命令回执单独记录。

目标变化时取消旧调度；仍有效的迟到响应通过有界关联恢复。等待超限后保留已有内容与显式重试入口，调度优先服务当前首屏和主动历史请求。

### 5. Host 在封帧之前去重和背压

Host 按设备和不可变请求身份合并任务，定向返回响应，在封帧前预留预算并完成准入。前台与后台调度共享有界资源，保持公平恢复。

重传遵守原任务归属、退避与保留预算；封帧后的密文保持原顺序和加密身份。Relay 负责不透明路由。诊断采用有界传输元数据，区分后端计算、排队与实际交付阶段。

### 6. 2026-10-23 容量调整

容量调整保留稳定事务身份、租约、前台优先、后台最多一个活动任务和封帧前字节预留。

| 参数 | 原值 | 调整后 |
|---|---:|---:|
| 每设备活动同步任务 | 2 | 4 |
| 每设备未完成同步任务（含活动任务） | 8 | 32 |
| 每设备保留的任务记录 | 32 | 128 |
| 每设备同步线路字节预算 | 6 MiB | 12 MiB |
| 同步投递记录上限 | 8 | 32 |
| 正常页明文预算 | 256 KiB | 512 KiB |
| Host 当前会话数量和每设备会话订阅数量 | 64 | 256 |
| Host 当前会话累计字节预算 | 8 MiB | 32 MiB |
| Host 历史页缓存数量 / 累计字节预算 | 64 / 8 MiB | 256 / 32 MiB |
| Registry 默认记录数 / 单值预算 | 512 / 256 KiB | 16,384 / 1 MiB |
| HostService Registry 记录数 | 4,096 | 16,384 |
| 普通状态快照预算 | 256 KiB | 512 KiB |

APP 历史分页为每页 30 条，未指定 `maxEntries` 时仍默认 30 条。真机日志显示 30 条首屏处理已耗时约 49–82ms，因此首屏也保留 30 条。

单响应硬上限仍为 1 MiB。`sessionSyncWireBytes(1 MiB)` 约为 2 MiB，12 MiB 足以预留四个完整响应，任务数与字节预算共同约束实际并发。APP 入站 `msg` 预算仍为 4 Mi 个 UTF-16 字符（ADR-0040），四个最大响应可容纳，持续过载仍按既有规则丢弃并重同步。缓存和记录按实际占用增长。

同步准入的字节预算只计 `ctl` / `msg` 队列，不再把有独立 64 MiB 预算的 `bulk` 排队字节算进 12 MiB 同步预算。此前 `mux.queuedBytes` 混合三类队列，文件下载即使没有占用任何同步预留，也能让小同步响应返回 `session_sync_busy_or_unavailable`。该条件不测量带宽，在 LAN、Relay 上执行相同的判断。真实同步及非 bulk 队列超预算仍拒绝；拒绝日志记录路径、原因、投递数、各类队列字节和本次预估字节，不含载荷正文。请求准入阶段的拒绝也记录任务数和预算；Host 将同步错误码及 commandId 写入既有有界持久诊断记录，Android 收到同步错误时写入 Logcat，不再只更新界面。

容量、准入、公平性和客户端恢复的验证以测试源码与实际证据为准；容量调整和实测吞吐分别记录。

2026-10-23 排队来源诊断：Host 在序列化前从业务对象提取消息类型、RuntimeEvent 类型、runtimeId、sessionId 和状态领域名，随已加密分片在内存中保留来源标签；不解析或保存消息正文，不改变线路格式、发送优先级或准入预算。每设备、每路径的非 bulk 队列达到 1 MiB 后，最多每 5 秒采样一次，使用既有有界持久诊断日志记录 `transport.queue` 分类。

每次采样包含一条 `outbound_queue_pressure` 汇总，以及最多八条 `outbound_queue_source` 来源记录，共用 operationId。汇总区分应用层非 bulk / bulk 排队与底层 socket 待发字节，记录采样窗口、窗口内非 bulk 入队字节、成功交付传输层的字节、写入异常次数和最长排队时间。成功交付 socket 不表示手机已收到或应用。来源记录按当前排队字节排序，附分片数和最大单消息明文字节；最多聚合 256 个来源分组，未展示与无法归属的字节分别通过 `otherSourceBytes` / `sourcesTruncated` 和 `unattributed` 标记。摘要和来源分行记录，遵守 Journal 每条最多 16 个详情字段、每字段最多 256 字符的既有限额，避免整份 JSON 详情被静默截断。采样复用发送调度器，不增加空闲轮询；断开、重新握手和关闭均随队列释放统计状态，诊断沿用既有投递与重试生命周期。

## Consequences

首屏和历史下载可以补充持久缓存，后续追赶复用这些数据，减少重复传输。代价是需要显式表示不完整缓存片段与连续覆盖，并统一处理写入冲突，由统一拥有者维护。

首屏不等待完整树或后台同步。一个有界页面先完成统一校验和事务，再按其显示用途投影；数据库失败保留既有内容并显示错误，不继续提交未经确认的 canonical 状态。

本 ADR 不新增三套同步接口，不改 Relay 业务职责，不把提高超时常量当作修复，不顺带优化 thread/list 探询。rollout 多文件选择只在影响 canonical 身份/历史完整性的证据确认后按对应 ticket 处理，不用“取最大文件”猜权威来源。

如实施需要改变线上 schema，遵循 ADR-0064 的共同版本、能力协商与已部署端兼容要求；Protocol/Relay 改动遵循仓库 CI 部署入口。设计偏离、预算变化或新增功能须更新对应决策与实现。
