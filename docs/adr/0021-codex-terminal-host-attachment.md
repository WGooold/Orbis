# ADR-0021: Terminal Codex attaches to the Host app-server

Date: 2026-09-26

Status: accepted.

## Context

A user who types `codex` in a Windows terminal should use the same Codex app-server that Orbis Host exposes to the phone. Replacing the npm-generated `codex.cmd` is fragile because package updates overwrite it and the selected Codex installation can change. A new app-server thread cannot be attached with `codex resume <id> --remote` before its first turn because Codex does not write the rollout until that turn.

## Decision

Orbis installs a managed `%LOCALAPPDATA%\\Orbis\\bin\\codex.cmd` shim ahead of other Codex entries in the user PATH. The shim intercepts only an argument-free interactive `codex` invocation. It reads the Host loopback descriptor, requests a short-lived local launch registration authenticated by that descriptor token, and runs the exact Codex CLI entry selected by Host with `-C <terminal directory> --remote <Host endpoint>`. `-C` is load-bearing: without it the official TUI creates its first thread in the app-server's own working directory, so the terminal session would run in the wrong directory and the cwd-keyed adoption could never match its registration. The official TUI creates the first thread and Host adopts the resulting `thread/started` notification for the pending terminal launch, matching it by working directory; the registration therefore outlives the official trust prompt that an untrusted directory triggers before any thread exists. Commands with arguments, including `login`, `exec`, `app-server`, `resume`, help, and provider-management commands, retain the normal Codex behavior; when Host is unavailable, the argument-free invocation falls back to the selected standalone Codex CLI.

The launch API is an HTTP route on the existing 127.0.0.1 loopback server. It is not exposed on LAN or Relay. Host and offline/parameterized shim launches share the Codex entry selected by Host, persisted under the Orbis agent-install root in `codex-selection.json`. Managed installation and version activation update this record; explicitly configured external entries and validated npm copies can also be selected by maintenance code. The Agent page exposes only update checks and an install/update-to-latest flow: it does not ask ordinary users to choose a version or installation source. The runtime updates a detected npm installation in place and uses a verified managed installation for other entries. The page reports CLI health, terminal integration and Host backend connectivity separately. Terminal integration is independently enabled or repaired (including in the portable build); failures do not undo a completed CLI download. Compatibility checks require both CLI `--remote` and app-server `--listen` before enabling integration. Windows resolves the machine PATH before the user PATH, so a `codex` that another tool installed machine-wide keeps winning however the user PATH is ordered. Terminal integration therefore treats that ordering as a repair rather than a warning: the same enable/repair action asks once for elevation and puts the Orbis bin first in the machine PATH, and uninstall removes that entry. The per-user installer never writes the machine PATH on its own, and it never replaces an npm-generated `codex.cmd`.

## Consequences

Terminal-first sessions become visible on the phone after the TUI creates its first thread. Multiple pending terminals in the same working directory are inherently ambiguous and are matched oldest-first; an explicit `codex resume <id>` remains an unmanaged official Codex invocation and is not retroactively claimed. Existing terminals need to be reopened after PATH installation. A machine-wide `codex` installed by another tool needs that single elevation before a bare `codex` reaches Orbis; until then the shim stays installed but unused. Host shutdown leaves the shim installed, but it transparently falls back to standalone Codex until Host is available again.
