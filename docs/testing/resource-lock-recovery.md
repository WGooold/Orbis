# 共享资源解锁责任与遗留锁恢复

2026-11-03 用户要求：所有使用共享资源的 agent 必须在使用结束后解锁，并明确 agent 忘记解锁时的处理方案。本规则适用于主 agent、子 agent、不同聊天、工作树、供应商及人工启动的回归任务，覆盖模拟器名额、启动锁、登记锁、设备锁、私有 ADB 端口锁和构建租约。

本文件是处理方案的维护源；本机同内容副本位于 `~/.orbis/tools/ui-regression/lock-recovery.md`，供所有工作树读取。本机 `AGENTS.md` / `CLAUDE.md` 的共享段包含强制要求。修改时同时更新共享副本与 `sync-agent-guides.py` 的规则文本，并运行同步器，不覆盖各工作树 UI 基线。

## 1. 每个 agent 必须执行的收尾

**谁取得资源，谁负责清理并核验解锁。完成测试、命令返回 0、发送中断或子 agent 回复“完成”，都不等于已经解锁。**

1. 借用前记录资源清单：owner、任务、工作树、证据目录、锁路径、设备 / 端口、入口及子进程身份。使用两端共用入口，命令保持前台；构建租约用上下文管理或 `try/finally` / `trap` 收尾，不脱离运行器留下后台任务。
2. 正常完成、失败、超时、取消和收到 SIGINT / SIGTERM 时，都先停止本任务子进程并等待退出；恢复并核对本任务更改的设备设置；关闭借用设备，核对 Android emulator / 私有 ADB 退出及端口空闲，或 iOS 为 Shutdown。构建结束还要核对自己的编译器、Java / Gradle / Kotlin 后代进程退出。
3. 通过原入口或租约对象按 owner 释放自己的设备 / ADB / 构建租约；临时登记锁、启动锁、全程名额也必须结束持有。系统 `flock` 释放的是持有关系，**不要删除 `simulator-run.lock` 或 `resource-startup.lock` 文件**，否则可能形成两个不同 inode 的锁。
4. 收尾时读取本次 `cleanup.json` / `result.json`，核对清理无错误、原 owner 不再占有资源、进程 / 端口 / 设备实际状态一致，再运行 `resource_guard.py queue`。若资源已被新 owner 正常借用，记录交接事实，不能删除新 owner 的锁。队列里其他任务的占用不代表自己的清理失败。
5. 不再使用资源时立即释放，再做文档整理、等待用户或无关长任务。正常最终回复要说明本任务资源已释放，并给出清理证据；未借用资源的任务无需制造清理记录。不得留下无人负责的后台任务后声称完成。

主 agent 委派资源任务时必须传达本规则，维护子任务资源清单，并核对各子任务的清理证据后再结束。委派不免除主 agent 的收尾核验责任。确需交接仍在使用的资源，接收方必须明确接受，并在同一互斥保护下完成 owner / 任务 / 进程元数据交接；仅发送消息或改任务名称不算交接。当前共用入口没有通用的运行中 owner 转移命令，普通任务应释放后由接收方重新排队。

清理失败时必须继续处理能安全处理的部分；无法退出的进程、无法确认的归属或无法恢复的设置，必须记录为 **`cleanup-required`，保留对应保护锁并明确交接阻塞**。这是异常未完成，不是正常解锁的例外捷径。强制结束进程或断电不能保证执行 finally，后续按下列恢复流程处理。

## 2. 发现占用时先判定什么

| 核查结果 | 必须执行的处理 | 能否释放遗留锁 |
| --- | --- | --- |
| owner 和任务仍在运行 | 等待原任务清理；需要结束时由原任务取消，或按用户已明确授权定向停止 | 不能抢占 |
| owner 已退出，所有相关进程已退出、端口空闲、设备关闭、设置恢复可核验 | 在维护互斥下归档、重新核对 owner，再定向释放 | 可以，见 §4 |
| owner 已退出，但其 emulator / ADB / 测试 / 构建后代仍在运行 | 核实完整身份后先结束这些遗留进程，再重新判定 | 进程结束且其他条件满足后才可释放 |
| SIGTERM / SIGKILL 后进程仍存在或端口仍被占用 | 保留保护锁和现场；说明需要系统层处理，必要时在用户安排重启电脑后复核 | 不能仅删除锁 |
| PID 被复用、owner 元数据缺失、设备状态读取失败、外接盘异常 | 保留现场，补足身份 / 状态证据；不得猜测或杀相同 PID 的新进程 | 不能释放 |
| 设置恢复未完成 / 无法确认 | 保留原设置及设备保护；进入定向恢复，未验证前不进入测试 | 不能宣称设备可复用 |
| `flock` 文件仍在，但无实际持有者 | 文件属于正常持久锁载体；继续检查目录租约与真实运行状态 | 无须删除文件 |
| 电脑重启后留有目录锁 | 系统释放 flock 不代表目录租约已清理；重新执行完整核查 | 满足相同条件后才可释放 |

锁龄、文件修改时间、心跳过期、聊天显示空闲、owner PID 不存在，都只能提示“需要检查”，不能单独作为抢占或删除依据。排队每 20 秒复查，等待期间至少每 60 秒报告具体 owner / 任务和阻塞原因。

## 3. 核查与取证

先运行只读诊断，不启动模拟器或 ADB 服务：

```sh
python3 "$HOME/.orbis/tools/ui-regression/resource_guard.py" queue
python3 "$HOME/.orbis/tools/ui-regression/resource_guard.py" status
python3 "$HOME/.orbis/tools/ui-regression/android-emulator.py" doctor
# iOS：把下方 UDID 换成 pool.json 登记的目标身份。
python3 "$HOME/.orbis/tools/ui-regression/ios-simulator.py" doctor --device <池内UDID>
```

`queue` 的无 holder / 无 blocker 不是所有资源都已清理的证明：它不替代 ADB 端口、构建租约及本任务清理日志的检查；遇到锁时也可能尚未扫描实际设备。核查者还必须：

- 从实际池目录读取目标 `owner.json`，按 owner 找到原证据中的 `session.json`、`original-settings.json`、`cleanup.json` 和 `result.json`；iOS 或早期任务没有某项文件时，使用已记录的设备 / 进程证据，不虚构文件存在。
- 核对 owner PID 与后代、启动时间、可执行文件、完整参数、进程组、工作目录、AVD / UDID、私有 ADB 端口和 emulator 端口。只看一个 PID 不能排除 PID 复用或父进程退出后遗留的子进程。
- 用 `ps` 查询精确候选身份，用 `lsof` 查询登记端口 / 构建目录的占用；iOS 读取 `xcrun simctl list devices --json`。设置有界超时；工具出错、无权限或超时记为未知，不把检查失败解释为没有占用。
- 构建租约按规范化目录路径的 SHA-256 查找；同时核对进程命令、工作目录和打开文件。没有打开文件只是辅助证据，不能单独证明构建已经结束。
- 在 `.artifacts/ui-regression/<日期>-<任务>/lock-recovery/` 保存前后快照、原 owner 元数据、原设置、观察时间和判断理由；仅保留必要运行信息，不收集凭证或会话正文。

## 4. 维护接管与释放顺序

这是一项定向维护操作，不是普通任务绕过队列的入口。目前没有通用的“一键清除全部旧锁”命令，也没有按锁龄自动解锁的服务。`doctor` / `queue` 只诊断，不回收。不得复制旧 `.artifacts` 下带固定 PID / owner 的清理脚本重复执行。

1. 明确本次可处理的 owner、设备、端口和租约。自己的遗留资源可继续完成清理；他人仍活跃的任务不得擅自结束。用户已明确授权清理的对象无需重复请求同一授权；系统重启等超出原范围的操作另行安排。
2. 由一个维护执行者以非阻塞方式取得现有 `simulator-run.lock` 文件的系统 flock，再取得 `registry.lock`；维护期间不启动设备、不分配新资源。维护锁也写入 owner / 任务 / PID / 证据，并用 finally 释放。若全程 flock 仍有人持有，停止维护并报告占用；不能另建池或替换 flock 文件绕过。
3. 若 `registry.lock` 本身是遗留项，在已持有全程 flock 的条件下，先核对登记锁 owner 已退出、没有仍在执行的登记 / 分配操作，归档并再次比对其 owner 后定向释放，随后正常重新取得 registry。无法排除旧登记操作时保持阻塞。
4. 在互斥内重读原 owner、会话和实际状态。任一 owner / 身份已变化则停止对该项的操作。对确认的孤儿进程先温和终止并有界等待；必要时才定向强制终止，发信号前再次核对身份。只有确认进程组全部属于该任务才能向组发信号。不得全局 `pkill java`、`gradle --stop`、`adb kill-server`、关闭全部模拟器或卸载外接盘。
5. 重新检查进程、端口、设备及设置。设置必须有恢复并核验的证据，或证明任务从未更改设置。进程没退出、设备状态未知或设置尚未恢复时，保留设备保护锁。若恢复需要重新启动设备，应先结束这一轮不启动设备的维护，保留保护与证据；通过共用入口内的定向恢复实现接管、80% 内存检查、单台限制和原设置恢复。当前没有通用的遗留会话设置恢复命令，需补齐该能力后再复用该设备；不能删锁、直接 boot 或由新任务把污染值当成原设置。
6. 仅在条件全部满足后，先归档目标锁元数据，再使用该锁原有的 owner 校验 / 释放方式定向移除。目录锁只移除已核验的元数据并删除空目录，不对锁目录递归删除；多出未知文件、内容变化或 owner 不匹配都停止该项。每个设备 / ADB 锁分别核验；不删除 pool.json、设备数据、构建目录或测试证据。
7. 构建租约单独处理：必须确认租约 owner、编译进程及后代都已退出，目录无活跃读写引用，再归档并按该租约原有的身份校验方式释放。模拟器清理成功不代表构建租约可以释放；若涉及不同锁机制，应按其原实现处理，不能把 flock 文件当作目录锁。
8. 在释放维护锁前保存变更后快照；退出后再次检查队列和本次 owner 的所有资源。新 owner 已接续使用时只记录，不再次清理。维护本身也执行 §1 的收尾要求，保留失败项而释放已完成的维护临时锁。

若设备此前已在“进程退出但设置未验证”的情况下解锁，仍属于待恢复设备，不能沿用“目录已删除，所以恢复完成”的判断。按原证据固定目标，在共用入口内完成设置恢复和核验后再用于测试。

## 5. 失败交接必须写清什么

异常最终回复与证据摘要必须包含：原任务 / owner、剩余锁绝对路径、设备 / 端口、仍存活的精确进程、已执行的清理及结果、保留原因、证据位置、下一步处理人 / 处理条件。不能只写“池子被占用”或“已经发 kill”。

建议记录字段：`status`（`released` / `cleanup-required`）、`originalOwner`、`recoveryOwner`、`resources`、`processChecks`、`settingsVerified`、`releasedLocks`、`retainedLocks`、`errors`、`nextAction`、`evidence`。没有接收方明确接受时，标注“未完成交接”，不把责任转给未知 agent。

2026-11-03 已遇到的现场：`provider-well-shadow-standard-full` 的 owner 已退出，但 `Orbis_UI_Polish_35` 的 emulator 在定向 SIGTERM / SIGKILL 后仍存在，5680 / 5681 仍被占用，因此保留设备 / ADB 锁。另一个旧任务的进程退出后锁已释放，但设置恢复尚未验证，仍须按上一节恢复。原始证据在 `.artifacts/ui-regression/20261103-claude-background-agents/pool-recovery/`；其中 PID 和快照只属于当时现场，每次操作必须重新核对。这些记录不代表当前全池可用，也不提升 App UI 验收状态。

## 6. 已实现范围与验证

共用入口已实现正常完成、失败、超时及 SIGINT / SIGTERM 的清理，以及清理失败保留设备锁；本次补充的是 agent 强制核验和遗留锁处置规则，不宣称已实现无人值守的孤儿回收或硬关机后的自动恢复。

文档变更执行 L0：规则链接、双入口一致、各工作树原 UI 基线不变；共享副本逐字一致。未来若修改恢复程序，必须用隔离临时目录 / 模拟进程覆盖正常清理、中断、owner 改变、PID 复用、活跃 owner 拒绝、旧 registry、设置未恢复、端口仍占用、不可终止进程和重启残留；不得为了测试强杀真实任务或绕过单台 / 内存门槛。设备与人工 UI 门禁仍按仓库 `docs/testing/ui-regression.md` 独立判断。
